# Remittance Processing EventsSource application name: `snowdrop-remittanceprocessing`A second source application, `Snowdrop.Ledger.Charges`, is registered in `RemittanceProcessingEventResources` for the Ledger Charge stream (entity type `"charge"`), but no event in this contracts library targets that stream — it is consumed cross-application. It is listed below for completeness but not documented further.---## Stream FormatsEach stream is identified as `ApplicationName->{OrganizationId}->EntityTypeName->{EntityId}`, built via `EventStreamIdentifier.Create(...)` in `RemittanceProcessingEventResources` (`src/runtime/Eventing/RemittanceProcessingEventResources.cs`).| Stream | Format ||--------|--------|| Remittance | `snowdrop-remittanceprocessing->{OrganizationId}->remittance-processing->{RemittanceId}` || Vendor | `snowdrop-remittanceprocessing->{OrganizationId}->remittance-processing-vendor->{OrganizationId}` || Reserved Funds | `snowdrop-remittanceprocessing->{OrganizationId}->remittance-processing-reserved-funds->{RemittanceId}` || Claim Payment | `snowdrop-remittanceprocessing->{OrganizationId}->remittance-processing->{RemittanceId}-{ClaimPaymentId}` || Ledger Charge (not documented — different source app) | `Snowdrop.Ledger.Charges->{OrganizationId}->charge->{ChargeId}` |**Notes on stream IDs:**- The Claim Payment stream uses the **same entity type name** (`remittance-processing`) as the Remittance stream, distinguished only by the composite id `{RemittanceId}-{ClaimPaymentId}`. In this codebase it is used for exactly one event: [`RemittanceClaimPaymentPosted`](#remittanceclaimpaymentposted), and only from the posting-queue backfill path (`PostingFlowOrchestrator.HandlePostingQueueRequest.cs`, `PublishMissingRemittanceClaimPaymentPosted`) — confirmed as the only call site of `CreateClaimPaymentIdentifier` in `src/runtime`.- The Vendor stream's id is the `OrganizationId` itself (not a distinct entity id) — it is effectively one stream per organization holding vendor-level settings ([`ReservedFundsEnabled`](#reservedfundsenabled), [`CompaniesUnlimitedRemittancesSet`](#companiesunlimitedremittancesset)).- Despite most claim-payment-scoped events implementing `IRemittanceClaimPaymentEvent` or `IRemittanceChargePaymentEvent` (which add `ClaimPaymentId`/`ChargePaymentId` to the contract), confirmed publish call sites (`RemittanceRTMediator`, `AssistanceCreditCardController`, `InsuranceCreditCardController`) write these to the **Remittance** stream, keyed only by `RemittanceId` — not to a separate per-claim-payment stream. The Claim Payment stream described above is the sole exception.- `RemittanceProcessingEventResources` also defines `Sequence`, `Rule`, `SequenceOrder`, and `RuleOrder` entity type constants (`remittance-processing-sequence`, `remittance-processing-rule`, etc.) used by `SequenceController`/`RuleController` for sequence and rule events (e.g. `SequenceStatusUpdated`, `RuleCreated`, `RuleRemoved`). None of those event types live in `src/contracts/Events`, so their streams are out of scope for this document.---## Base ClassesThis library uses marker **interfaces**, not abstract base classes, to group events (all in `src/contracts/Events/RemittanceProcessing/`):### `IRemittanceProcessingEvent`Provides `RemittanceId` (`Guid`). The great majority of remittance-scoped events implement this.### `IRemittanceClaimPaymentEvent : IRemittanceProcessingEvent`Adds `ClaimPaymentId` (`Guid`).### `IRemittanceChargePaymentEvent : IRemittanceClaimPaymentEvent`Adds `ChargePaymentId` (`Guid`).**Notes:**- A few events deviate from this hierarchy despite carrying the same-shaped data: [`RemittanceIsArchived`](#remittanceisarchived) implements no interface at all. [`RemittanceClaimPaymentAggregated`](#remittanceclaimpaymentaggregated) carries a `ClaimPaymentId` property but implements only `IRemittanceProcessingEvent`, not `IRemittanceClaimPaymentEvent`. [`RemittanceClaimPaymentDiscarded`](#remittanceclaimpaymentdiscarded), [`RemittanceClaimPaymentsDiscarded`](#remittanceclaimpaymentsdiscarded), [`RemittanceReverseClaimPaymentDiscarded`](#remittancereverseclaimpaymentdiscarded), [`RemittanceClaimPaymentRemoved`](#remittanceclaimpaymentremoved), and [`RemittanceReverseClaimPaymentRemoved`](#remittancereverseclaimpaymentremoved) likewise carry `ClaimPaymentId` but implement only `IRemittanceProcessingEvent`.- The Reserved Funds and Vendor events (`ReservedFundsEnabled`, `CompaniesUnlimitedRemittancesSet`, and all `RemittanceProcessingReservedFunds*` events) implement none of these interfaces — they are plain records.- `RemittanceProcessingEventList` (`RemittanceProcessingEventList.cs`) is a helper `IEnumerable<IRemittanceProcessingEvent>` wrapper used to batch events before publishing; it is not itself an event.---## Model Types### Enums#### `CheckPaymentStatus``NotTaken = 0` (Payment Not Taken), `Taken = 1` (Payment Taken, Not Deposited), `Deposited = 2` (Payment Taken and Deposited)#### `CheckPostingStatus``Unknown = 0`, `New = 1`, `Reconciled = 2`, `Posting = 3`, `Posted = 4`, `Empty = 5`, `Building = 6`, `Ready = 7`, `Discarded = 8`, `Archived = 9`#### `ClaimPostingStatus``Unknown = 0`, `Ready = 1`, `Posting = 2`, `Posted = 3`, `Discarded = 4`, `Excluded = 5`, `Removed = 6`#### `ReasonCodeCategory``UnKnown = 0` (typo preserved — capital K), `Adjustment = 1`, `Transfer = 2`#### `DisputeTypes` (`[Flags]`)`None = 0`, `User = 0x1`, `Denial = 0x10`, `Transfer = 0x20`, `Underpayment = 0x40`.
